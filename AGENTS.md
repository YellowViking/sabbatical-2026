# AGENTS.md

Main agent instructions for this repo live in [`.github/copilot-instructions.md`](.github/copilot-instructions.md) — read that first. This file adds rules that apply to **every** agent working here.

## API first — always (user rule, 7 Oct 2026)

**Every browser task starts from an API, not from clicks.** In order:
1. Look for the endpoint in the table below.
2. Otherwise use the site's own XHR/fetch, a public JSON/HTML endpoint you can `curl`, or a published file (PDF, image, JSON).
3. Drive the UI **only once**, to capture the request (then replay it), or when nothing structured exists (e.g. starring a place, choosing a list icon). Say so when you fall back.

This applies even to one-off lookups. On 7 Oct, UI loops cost many turns: clicking each place into Maps lists when `maps-lists.js createitem` exists, scraping review panels, and typing into the poster-timetable form.

If you are about to load-and-scrape the **same kind of page more than ~3 times** (cities × dates, properties, review pages, fare calendars), **stop and refactor before looping**:

1. **Capture the request the page makes.** Open one real page with CDP `Network.enable` (or DevTools) and log the XHR/fetch that returns the data — URL, method, `postData`, and the non-cookie headers.
2. **Decode the payload** and find the fields that vary (origin, destination, date, filters, currency).
3. **Replay it in batch** with `fetch` from inside a tab on the same origin (so the user's session applies), with modest concurrency, instead of one page load per query.
4. **Write down the recipe** (endpoint, payload layout, parsing, gotchas) in a skill or memory note so the next session starts from the API, not the UI.

A page-per-query loop is the fallback, not the default: it took ~17 min for a 50-city fare sweep that the replayed API did in ~80 s.

**Guardrails**

- **Detect silent throttling.** Batch endpoints may return HTTP 200 with *empty* results under load — indistinguishable from "no data". Retry empties slowly (≤2 workers, ~600–900 ms apart); only trust a gap once a retry finds nothing new.
- **Push for direct data fetch (user, 25 Nov 2026: "you should try to automate direct data fetch as much as possible").** When an API refuses a replay (403, an HTML block page), don't fall back to the UI straight away. Work down this list:
  1. Replay from a tab on the site with `credentials:'include'` and the page's exact non-cookie headers.
  2. Call the site's own client code.
  3. Let the page send its own requests and rewrite their payloads with Playwright `page.route` (the LifeMiles method).
  4. Drive the UI.
  Captchas and sign-ins still go to the user. Keep the pace polite.
- **Keep secrets out of the repo.** Captured session tokens, cookies and replay scripts that embed them stay outside the repo (e.g. `~/.local/share/`), never in commits.
- Keep concurrency polite (≈4 parallel, short delays) and stop on the first 429.

## Browser automation: which tool

1. **A replayable API** (the table above), from a tab via `fetch`. Cheapest by far.
2. **Playwright over CDP, run from Bash:** `node ~/.local/share/cdp-tools/pw.mjs <script.mjs> [url]`. It attaches to the logged-in Chrome on :9222, opens its own tab and runs `export default async (page) => result`. Use `getByRole` / `fill` / `click` locators, and print **only** the returned value; this is the default for UI forms. Example: `/tmp/cd-graz.mjs` (cd.cz search, 3 lines of output).
3. **The VS Code browser tools (`mcp__client__*`)** run in a separate browser that isn't logged in, and they append a full accessibility snapshot to every call (~10k+ tokens per action). Use them only for a quick look.
4. **Playwright MCP (`mcp__playwright__*`, attached to :9222)** is the fallback when a scripted read fails on a site's widget (calendars, iframes, booking engines). **Finish the check yourself; never hand it back to the user** unless a login or captcha needs them. Example: Rynek 30's Previo engine (`booking.previo.app/index/step-1/?hotId=785771`): click the Departure field, then `a.ui-state-default` with the day, then Continue.
5. **Hand-built CDP action JSON (`cdp-act.mjs`)** is the last resort. Its quoting and selector fiddling wasted many turns on 6 Oct.

Also ask Google ("train <A> to <B> <date>"): its "Transport websites" box names the first-party sellers.

## The traveller

- **The user is male.** Never suggest, price or list **female-only** dorms, rooms or hostels (e.g. "Female Dormitory", GIRLSTEL, Women's Only Hostel). Filter them out of every sweep, and when a hostel's only free beds are female-only, treat it as **sold out**.
- Travels solo: always search for **1 adult**.

## Private-room sweeps: read the room list, not the card

A search card (Booking, Chase, Agoda) shows only the property's **cheapest unit**. Hostels therefore look like €20 dorms, and their private twins never surface. On 7 Oct this hid Rynek 30's $80 private twin and VICE CITY's €54 twin. For private-room searches:
1. Include hostels (`ht_id=203`) and cheap aparthostels.
2. Fetch every candidate's room table (Booking `#hprt-table`; Chase `hotel/rooms/rates`).
3. Keep the cheapest room whose name has no dorm / bed in / bunk / women / female.
4. Rank on that price.

## Lodging prices: triple-check every city

Booking.com is not always the cheapest. In Białystok (6 Oct 2026), Chase Travel was €30 cheaper on the same property. For each city, before recommending a bed:

1. **Google Hotels first, as the index.** It lists Booking, Expedia, Hotels.com, Priceline, Agoda and the property's own site. Follow "Visit website" for direct rates.
2. **Booking.com** (with Genius) is the source for review distribution and the location score, which are the quality filters.
3. **Chase Travel** (while the $100 hotel credit lasts). Create the search with **1 adult**, because the UI defaults to 2.
4. **Expedia / Hotels.com / Priceline / Agoda** where Google omits them.

Report the cheapest channel per property. Match properties across channels by name.
